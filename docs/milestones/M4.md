# M4: Reminder Engine

## Status: COMPLETE

## What Changed

### Domain Layer
- **`domain/reminder_job.rs`**: New `ReminderJob` entity and `ReminderJobStatus` enum (`Pending`, `Scheduled`, `Fired`, `Canceled`, `Failed`).
- **`domain/reminder_calc.rs`**: Pure function `compute_fire_at(task, global_default, now, zone)` that calculates the fire time for a reminder based on task schedule, reminder preference, and global default. Handles DST gaps/overlaps correctly.

### Repository Layer
- **`repo/reminder_job_repo.rs`**: `ReminderJobRepository` trait with methods: `insert`, `get`, `list_by_task`, `list_due`, `update_status`, `cancel_active_by_task`.
- **`repo/sqlite/reminder_job_repo.rs`**: SQLite implementation with full test coverage.

### Scheduler Layer
- **`scheduler/mod.rs`**: `NotificationSender` trait, `TauriNotificationSender` (production), `FakeNotificationSender` (tests), `SchedulerError` enum.

### Application Layer
- **`app/reminder_service.rs`**: `ReminderService` with:
  - `reconcile_task(task_id)`: Idempotent reconciliation for a single task.
  - `reconcile_all()`: Reconcile all tasks (called on startup and global default change).
  - `poll_due()`: Check for due reminders and fire notifications.
  - `cancel_for_task(task_id)`: Cancel all active reminders for a task.
  - Full test suite with fake repositories.

### Tauri Integration
- **`lib.rs`**:
  - Added `ConcreteReminderService` type alias.
  - Wired `ReminderService` into all task mutation commands (`create_task`, `update_task`, `reschedule_task`, `complete_task`, `undo_completion`, `cancel_task`, `restore_canceled_task`, `soft_delete_task`).
  - Added `get_global_reminder_default` and `set_global_reminder_default` commands.
  - Startup reconciliation in a background thread.
  - Background polling loop (30s interval) in a background thread.
  - `set_global_reminder_default` triggers `reconcile_all()`.

## What Was Not Tested
- **Real OS notification delivery**: `TauriNotificationSender` uses `tauri-plugin-notification` but actual notification display requires a running GUI session. The `FakeNotificationSender` tests verify the logic path.
- **Windows/Linux notification behavior**: Only macOS is available in the dev environment.
- **Long-running polling stability**: The 30s polling loop is tested for logic but not for multi-hour stability.

## Known Risks
1. **Notification permission**: If the user denies notification permission, `poll_due` will log failures but continue. The `permission_granted()` check is available for UI to prompt.
2. **Thread safety**: The polling thread and command handlers share `Arc<ReminderService>`. SQLite connections are `Mutex`-guarded, so this is safe but may serialize under load.
3. **DST edge cases**: `compute_fire_at` handles gaps (returns `None`) and overlaps (earliest occurrence). This is correct per ADR 0006 but should be verified with real-world timezone data.
